# 3. Run Applications as Containers and Pods

### Pod-Phasen (`status.phase`)

| Phase | Bedeutung |
|-------|-----------|
| Pending | Pod wurde vom API-Server akzeptiert, aber mindestens ein Container ist noch nicht gestartet (z. B. Image wird noch gezogen, Scheduling läuft, Volumes werden gemountet) |
| Running | Pod wurde einem Node zugewiesen, alle Container sind erstellt und mindestens ein Container läuft (oder startet/restartet gerade) |
| Succeeded | Alle Container im Pod wurden erfolgreich beendet (Exit-Code 0) und werden nicht neu gestartet – typisch für Jobs/Batch-Prozesse |
| Failed | Alle Container wurden beendet, mindestens einer davon mit einem Fehler (Exit-Code ≠ 0) oder durch das System terminiert |
| Unknown | Der Zustand des Pods konnte nicht ermittelt werden – meist bei Kommunikationsproblemen mit dem Node (z. B. Node nicht erreichbar) |

### Container States

| Container State | Bedeutung |
|------------------|-----------|
| Waiting | Container ist noch nicht lauffähig (z. B. Image-Pull läuft, `ImagePullBackOff`, `CrashLoopBackOff`) |
| Running | Container läuft ohne Probleme |
| Terminated | Container wurde beendet – erfolgreich oder mit Fehler (mit Exit-Code und Grund sichtbar) |

### Pod Conditions

| Condition | Bedeutung |
|-----------|-----------|
| PodScheduled | Pod wurde einem Node zugewiesen |
| Initialized | Alle Init-Container wurden erfolgreich abgeschlossen |
| ContainersReady | Alle Container im Pod sind bereit |
| Ready | Pod ist vollständig bereit und kann Traffic empfangen (relevant für Services/Endpoints!) |

**Unterschied Deployment vs. oc new-app**
- Erzeugte Objekte: new-app erzeugt auch Service bzw. Imagestream
- Environment Variablen: env kann ich nur in new-app angeben, in Deployment nur im Nachgang
- Quellen: new-app kann aus Image, Git, Template und lokalen Verzeichnis deployed werden
- Automatisierung: ist in new-app hoch 

**Allgemeine Regeln UID/GUI in OpenShift**

- UID wird durch Openshift überschrieben, wenn Standard-SCC restricted genutzt, dabei wird UID aus projektspezifischen Range genutzt (z.B. 1000680000–1000689999, pro Namespace unterschiedlich)
- Der im Dockerfile gesetzte User (z.B. 1001) wird also überschrieben, es sei denn es wird das anyuid SCC genutzt
- GID sollte auf relevanten Verzeichnissen auf root-Gruppe 0 gesetzt werden

**Deployment vs. Job**

- unterschiedliches Selbstheilungsverhalten
- Deployment: Pod löschen → wird automatisch neu erstellt weil der Deployment-Controller ständig dafür sorgt, dass die gewünschte Anzahl Replicas läuft
- Job: Pod löschen, nachdem der Job bereits abgeschlossen ist → wird nicht neu erstellt weil der Job sein Ziel (COMPLETIONS: 1/1) schon erreicht hat — Job wird nicht gelöscht
- Job: "restartPolicy: Never" - Deployment: "restartPolicy: Always"

## Kubernetes Pod and Service Networks

<details>
<summary>Ausklappen Pod Networks</summary>

- Jeder Pod bekommt automatisch eine eigene IP aus einem gemeinsamen CIDR-Bereich – alle Pods liegen im selben flachen Subnetz, daher ist kein NAT für Pod-zu-Pod-Kommunikation nötig, auch nicht über Node- oder Namespace-Grenzen hinweg.
- Container innerhalb eines Pods teilen sich IP und MAC-Adresse und erreichen sich gegenseitig über localhost – das ist aber nur pod-intern sichtbar.
- Pod-IPs sind instabil: Bei Neustart, Skalierung oder Ausfall vergibt Kubernetes eine neue IP.
- Service bekommt stabile IP und fungiert als virtueller LB - fällt ein Pod aus aktualisiert Kubernetes automatisch die Service Endpoints
- Services wählen ihre Ziel-Pods über Label-Selectoren
- FQDN des Service: SVC-NAME.PROJECT-NAME.svc.CLUSTER-DOMAIN 
- /etc/resolf.conf wird bei Podstart automatisch durch DNS-Operator/Kubelet generiert
</details>


## Scale and Expose Applications to External Access

**Service-Typen**
- **ClusterIP** (Standard): nur clusterintern erreichbar, für Pod-zu-Pod-Kommunikation.
- **LoadBalancer**: provisioniert einen Load Balancer beim Cloud-Anbieter mit extern erreichbarer IP 
- **ExternalIP**: leitet Traffic von einer virtuellen IP auf einem Node an einen Pod weiter – als Legacy-Feature aus - Sicherheitsgründen nur bei Bedarf verwenden.
- **NodePort**: exponiert einen Service auf einem festen Port (Standardbereich 30000–32767) auf jedem Node – erfordert strikte - Firewall-Regeln, da direkte Verbindungen zu Nodes nötig sind.
- **ExternalName**: mappt einen Service per CNAME-Eintrag auf einen externen DNS-Namen.

**Gateway-API**
- **GatewayClass** - clusterweite Controller-Konfiguration
- **Gateway** - namespace-scoped Netzwerk-Einstiegspunkt (Listener,Ports,TLS)
- **HTTPRoute** - Regeln, wie eingehender Traffic auf Services gemappt wird

**Ingress-Objekte**
- Standard-Kubernetes-Alternative zu Routes, unterstützt HTTP, HTTPS, SNI und TLS mit SNI. 
- Wird ebenfalls vom OpenShift-Ingress-Controller verarbeitet. 
- Routes bleiben aber wegen erweiterter Funktionen und nativer Integration die bevorzugte Wahl.

**Sticky Sessions**
- Für zustandsbehaftete Anwendungen sorgt der Ingress-Controller per Cookie dafür, dass ein Client immer denselben Pod erreicht 
- konfigurierbar über oc annotate sowohl für Ingress als auch für Route-Objekte. 
- Bei Passthrough-Routes funktioniert das nicht, da der Router den verschlüsselten Traffic nicht einsehen kann.



Beispiel: Route erstellen und sticky sessions aktivieren:

```bash
oc expose deployment satir-app --name satir-svc \                   # Service
--port 8080 --target-port 8080

oc expose service satir-svc --name satir                            # Route

oc scale deployment satir-app --replicas 2                          # Skalierung

oc annotate route satir \                                           # Sticky Sessions
router.openshift.io/cookie_name="hello"
```

Beispiel: Ingress erstellen und sticky sessions aktivieren:
```bash
oc expose deployment sakila-app --name sakila-svc \                 # Service
--port 8080 --target-port 8080

oc create ingress ingr-sakila \                                     # Ingress
--rule "ingr-sakila.apps.lab.example.com/*=sakila-svc:8080"

oc scale deployment skrila-app --replicas 3                          # Skalierung

oc annotate ingress ingr-sakila \                                   # Sticky Sessions
ingress.kubernetes.io/affinity=cookie

```

Curl mit Cookie auf Client Seite:
```bash
curl ingr-sakila.apps.lab.example.com \                             # cookie wird erstellt
-c /tmp/cookie_jar

for i in {1..10}; do \                                              # Test sticky sessions
curl ingr-sakila.apps.lab.example.com -b /tmp/cookie_jar; done


```

## Persistente Daten-Volumes bereitstellen

### Grundkonzept: PV und PVC
- **PersistentVolume** (PV): Von Cluster-Administratoren bereitgestellte Storage-Ressource, clusterweit verfügbar (nicht projektgebunden).
- **PersistentVolumeClaim** (PVC): "Bestellung" eines Developers für Storage – ohne Kenntnis der zugrundeliegenden Infrastruktur. Projektgebunden, nicht zwischen Projekten teilbar.

### Zwei Provisionierungsarten:
- **Statisch:** Administrator legt PVs manuell an
- **Dynamisch:** Über StorageClasses werden PV automatisch bei Bedarf erzeugt

### Storage-Typen

| Typ       | Beschreibung |
|-----------|--------------|
| configMap | Externalisiert Konfigurationsdaten, versionierbar |
| emptyDir  | Pod-lokales Scratch-Verzeichnis, ephemeral |
| hostPath  | Mountet Verzeichnis vom Host-Node – nicht produktionstauglich, nur für Test/Entwicklung auf Single-Node-Clustern |
| iSCSI     | IP-basierter Block-Storage-Zugriff |
| local     | Lokale Disk/Partition, abhängig von Node-Verfügbarkeit |
| NFS       | Von mehreren Pods gleichzeitig nutzbar; laut Red Hat nur für Nicht-Produktivsysteme empfohlen |

### Zugriffsmodi (Access Modes)

| Modus            | Kürzel | Bedeutung |
|------------------|--------|-----------|
| ReadWriteOnce     | RWO   | Ein Node mountet read/write (mehrere Pods auf diesem Node möglich) |
| ReadWriteOncePod  | RWOP  | Nur ein einzelner Pod im Cluster mountet read/write |
| ReadOnlyMany      | ROX   | Viele Nodes mounten read-only |
| ReadWriteMany     | RWX   | Viele Nodes mounten read/write |

### Unterstützung je Volume-Typ

| Typ       | RWO | RWOP | ROX | RWX |
|-----------|:---:|:----:|:---:|:---:|
| configMap | ✅  | ✅   | ❌  | ❌  |
| emptyDir  | ✅  | ✅   | ❌  | ❌  |
| hostPath  | ✅  | ✅   | ❌  | ❌  |
| iSCSI     | ✅  | ✅   | ✅  | ❌  |
| local     | ✅  | ✅   | ❌  | ❌  |
| NFS       | ✅  | ✅   | ✅  | ✅  |

### Lifecycle von PV/PVC
| Status    | Bedeutung |
|-----------|:---|
| Available	| PV erstellt, für jede PVC im Cluster nutzbar |
| Bound	    | PV an eine PVC (und damit an deren Namespace) gebunden – exklusiv |
| In use	  | Aktiv von einem Pod genutzt; Storage Object in Use Protection (standardmäßig aktiv) verhindert vorzeitiges Löschen |
| Released	| PVC wurde gelöscht, Storage kann zurückgewonnen werden |
| Reclaimed	| Je nach Reclaim Policy: Retain (manuelle Wiederverwendung) oder Delete (PV und zugehöriger Storage in der Infrastruktur werden gelöscht) |

### Anlegen von PCV
- 💡 TIPP: über Konsole anlegen!
- erst Deployment anlegen
- dann ins Deployment gehen und über Actions -> Add storage das PVC anlegen
- Im PVC sieht man auch den Namen des PV

### Storage Class
Beispiel:
```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: io1-gold-storage
  annotations:
    storageclass.kubernetes.io/is-default-class: 'false'
    kubernetes.io/description: Provides RWO and RWOP volumes
parameters:
  type: io1
  iopsPerGB: "10"
provisioner: ebs.csi.aws.com
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
```

```bash
# storage classes abholen
oc get sc
```

| Feld	| Bedeutung |
|---------------|:---|
| parameters |	Provisioner-spezifisch (z. B. type, iopsPerGB bei EBS); nicht gesetzte Werte nutzen Provisioner-Defaults |
| provisioner	| Quelle des Storage-Plugins; Namen mit Präfix kubernetes.io sind standardmäßig verfügbar |
| reclaimPolicy	| **Delete** (Standard, automatische Löschung d. PV bei Löschung PVC) oder **Retain** (kein Datenverlust bei falscher PVC-Löschung) |
| volumeBindingMode	| **Immediate** (Standard): PV wird sofort bei PVC-Erstellung angelegt **WaitForFirstConsumer**: PV wird erst erstellt, wenn ein Pod die PVC tatsächlich nutzt |
| allowVolumeExpansion |	true erlaubt nachträgliche Vergrößerung (nicht Verkleinerung) über Bearbeitung der PVC |

## Non-shared Storage mit Stateful Sets verwalten

**File Storage**
- bietet gewohnte Verzeichnisstruktur, ideal für organisierte Daten, einfach zu verwalten
- Einsatzzeck: Sharing, Backup, Web-Content
- Protokoll-Bsp: NFS; SMN

**Block Storage**
- bietet Zugriff auf rohe Block-Devices (z. B. via SAN oder iSCSI) – wie physische Festplatten, die formatiert und gemountet werden müssen. 
- Kommunikation erfolgt direkt auf Geräteebene statt über die Betriebssystemschicht → schneller, 
- Einsatzzweck: Datenbanken, VMs, High-Performance
- Protokoll-Bsp: SAN, iSCSI

**Statefule Sets**
- abhängig von vergangenen Zuständen/Transaktionen
- vereinfacht die Wiederherstellung nach Ausfällen, da von definierten Punkt aus fortgesetzt werden kann
- StatefulSet repräsentiert Gruppe von Pods mit konsitenter Identität -> stabiler DNS/Hostname und eigener Storage Zuordnung pro Pod
- StatefulSet garantiert, dass bestimmte NW-Identität immer derselben Storage-Identität zugeordnet bleibt
- Pods werden sequenziell erstellt (nicht parallel wie Deployment) - erst nach Ready startet nächster Pod
- pro Pod wird automatisch ein PVC erzeugt
- PVC bleiben nach Löschen der SFS erhalten (müssen manuell gelöscht werden)

### Deployment vs. StatefulSet – der zentrale Unterschied

| Merkmal | Deployment | StatefulSet |
|---------|-----------|-------------|
| Standardeinsatz | zustandslose Anwendungen | zustandsbehaftete Anwendungen |
| Persistenter Storage | optional, eine gemeinsame PVC für alle Replicas | eine eigene PVC pro Pod, kein Sharing |
| Pod-Namen | zufällig generiert (z. B. `app-6694-5kpd`) | stabil & vorhersagbar: `<name>-<ordinalzahl>` (z. B. `dbserver-0`) |
| Start-/Skalierverhalten | Replicas parallel, unabhängig | sequenziell nach Ordinalzahl, wartet auf "Ready" des Vorgängers |
| Erstellung | `oc create deployment`, `oc new-app` (imperativ möglich) | nur per YAML-Manifest – keine imperativen `oc`/`kubectl`-Befehle |
| Nutzung | z. B. Webserver, Frontend | z. B. Datenbank-Cluster, verteilte Systeme |

**Headless Service**
- SFS benötigt zwingend einen Headless Service
- Im Gegensatz zu einem normalen Service (mit einer festen clusterIP fürs Load Balancing) hat ein Headless Service keine ClusterIP (clusterIP: None)
- Bei DNS-Abfrage liefert ein Headless Service die IP-Adressen aller einzelnen Pods zurück, statt über einen LB zu vermitteln
- deshalb bekommt jeder Pod im StatefulSet seinen eigenen vorhersagbaren DNS-Eintrag
<pod-name>.<service-name>.<namespace>.svc.cluster.local
- das ist essenziell für Peer-Discovery und direkte Pod-zu-Pod Kommunikation wie bei verteilten DB wo bestimmte Pods gezielt für  Schreib/Replikationsvorgänge angesprochen werden müssen

# 6. Configure Applications for Reliability

## Application High Availability

OpenShift erwartet von Anwendungen, dass sie:

- Neustarts tolerieren
- auf Health Probes reagieren (Startup, Readiness, Liveness)
- mehrere gleichzeitige Instanzen unterstützen
- ein klar definiertes, gutartiges Ressourcenverhalten haben
- mit eingeschränkten Rechten laufen


### Die drei HA-Techniken von Kubernetes

| Technik | Beschreibung |
|---------|--------------|
| Restarting Pods | Über eine Restart Policy startet der Cluster fehlerhafte Instanzen neu |
| Probing | Health Probes erkennen, wenn Anwendungen nicht mehr antworten, und lösen automatisch Gegenmaßnahmen aus |
| Horizontal Scaling | Bei schwankender Last skaliert der Cluster die Anzahl der Replicas passend |

### Pods neu starten - Restart Policy

Ein Container in einem Pod kann aus verschiedenen Gründen terminieren. Das Feld `restartPolicy` in der Pod-Spezifikation steuert, ob der kubelet die Container des Pods neu startet. Der Standardwert ist `Always`.

| Policy | Beschreibung |
|--------|--------------|
| Always | Der kubelet startet einen beendeten Container immer neu (Standard) |
| OnFailure | Der kubelet startet einen beendeten Container nur neu, wenn er mit einem Exit-Code ungleich 0 beendet wurde |
| Never | Der kubelet startet einen beendeten Container nie neu  |

- OnFailure und Never sind typisch für Jobs/Batch-Workloads -> Pod soll nach erfolgreichem Abschluss (Phase Succeeded nicht erneut starten)
- bei Deployments und StatefulSet ist nur always erlaubt

### 1. Ausfallbehandlung auf Container Ebene:
- Kubelet startet abgestürzten Container per RestartPolicy neu - mit wachsendem Backoff 
- CrashLoopBackOFF: Container ist abgestürzt, kubelet hat Neustart geplant und wartet gerade
- Backoff wächst zwischen den Starts exponentiell (10 s → 20 s → 40 s → 80 s → 160 s → max. 300 s (5 Minuten))
- COntainer behält Namen, IP und Zähler RESTART in oc get pods steigt

### 2. Ausfall auf Pod Ebene:
- Bsp: Node fällt aus, Pod wird evicted, jemand löscht pod
- Controller vergleicht Soll (z.B. replicas: 3)  mit Ist-Zustand (2 POds), stellt Differenz statt ud erzeugt neuen Pod
- Scheduler platziert Pod dann auf gesunden Node
- Pod wird nie neu gestartet, nur ersetzt


### Probe-Typen

Es gibt drei Typen. Je nach Anwendung konfiguriert man einen oder mehrere.

### Probe-Typen im Detail

| Probe | Zweck | Läuft wann? | Bei Fehlschlag | Typischer Einsatz |
|-------|-------|-------------|----------------|-------------------|
| Startup | Ist der Startvorgang abgeschlossen? | Nur beim Start, nach dem ersten Erfolg nicht mehr | Container wird gemäß `restartPolicy` neu gestartet | Anwendungen mit langer Startzeit |
| Readiness | Kann die Anwendung Anfragen bedienen? | Während der gesamten Laufzeit, auch nach einem Fehlschlag | Pod-IP wird aus dem Service entfernt, kein Neustart. Bei erneutem Erfolg wird sie wieder aufgenommen | Temporäre Probleme (Cache laden, Verbindungen aufbauen, lange Batch-Jobs) |
| Liveness | Ist der Container gesund? | Während der gesamten Laufzeit, erst nach Abschluss des Starts | Container wird gemäß `restartPolicy` neu gestartet | Hängende Anwendung, Deadlock |

```yaml
apiVersion: apps/v1
kind: Deployment
# ...
spec:
  template:
    spec:
      containers:
        - name: web-server
          livenessProbe:
            failureThreshold: 6
            periodSeconds: 10
            httpGet:
              path: /health
              port: 3000
```
### Felder einer Probe im YAML

| Feld | Bedeutung |
|------|-----------|
| `livenessProbe` | definiert eine Liveness Probe |
| `failureThreshold` | wie oft die Probe fehlschlagen muss, bevor reagiert wird |
| `periodSeconds` | Intervall zwischen 2 Prüfungen |
| `httpGet` | HTTP-Request als Test-Art |
| `path` / `port` | Pfad und Port des Requests |

### Probe hinzufügen 
Alternative: über Web -> Deployments --> add Health Checks
```bash
oc set probe deployment/front-end \
  --readiness \
  --failure-threshold 6 \
  --period-seconds 10 \
  --get-url http://:8080/healthz
```

### Test-Arten

Bei jeder Probe muss eine der folgenden Test-Arten angegeben werden:

| Test-Art | Ablauf | Erfolg wenn |
|----------|--------|-------------|
| HTTP GET | Cluster sendet einen HTTP-GET-Request an den Endpunkt | Antwortcode zwischen 200 und 399 |
| Container command | Cluster führt einen Befehl im Container aus | Exit-Code 0 |
| TCP socket | Cluster versucht, einen Socket auf dem angegebenen Port zu öffnen | Verbindung kommt zustande |

## Reserving Compute Capacity for Applications

Pod-Schedulung in 3 Schritten
1. **Nodes filtern**: Pod kann NodeSelektor definieren, nur Nodes mit passenden Labels kommen infrage, wenn Ressource Requests definiert, bleiben nur Nodes mit genügend Ressourcen übrig
2. **Nodes bewerten**: Scheduler berechtet Score für jeden Node anhand mehrerer Kriterien -> je höher desto besser
3. **Node auswählen**: Scheduler sortiert die Kandidaten und bei gleichem Score wird im Round Robin gewählt, anschließend wird ein Scheduled-Event für den Pod vom Cluster erzeugt

Request und Limit im bestehenden Deployment setzen
```bash
oc set resources deployment hello-world-nginx \
  --requests cpu=100m,memory=1Gi

oc set resources deployment/hello --limits memory=1Gi

# Überwachen des tatsächlichen Ressourcenverbrauchs:
oc adm top pods

oc adm top node master01

# Pods, die keinen Node finden
oc get events --field-selector reason="FailedScheduling"
```

Request und Limits im Deployment
```yaml
apiVersion: apps/v1
kind: Deployment
spec:
  containers:
    - image: registry.access.redhat.com/ubi9/nginx-120:1-86
      name: hello
      resources:
        requests:
          cpu: 100m
          memory: 500Mi
        limits:
          cpu: 200m
          memory: 1Gi
```

### Allocatable Wert 
- Allocatable = Node Capacity − system-reserved − Hard-Eviction-Thresholds
- bestimmt, wie viele Pods der Scheduler auf einem Node platzieren kann. 
- Erreicht die Summe aller Requests auf einem Node den Allocatable-Wert, plant der Scheduler dort keine weiteren Pods ein
- Summe der Limits darfalso über 100 % liegen (Overcommit), die Summe der Requests nicht.

### Requests vs. Limits

| | Request | Limit |
|---|---------|-------|
| Bedeutung | garantiertes Minimum, Grundlage fürs Scheduling | Obergrenze, die der Container nicht überschreiten darf |
| Wirkt bei | Scheduling | Laufzeit |
| Bei Überschreitung | (nicht anwendbar) | CPU: Drosselung (Throttling). Memory: Container wird per OOM-Kill beendet |

## Limits

### Memory Limits
- Memory ist **nicht komprimierbar** – kann einem laufenden Prozess nicht "weggenommen" werden
- Ohne Limit: Grenze ist der gesamte **Node**-Speicher → bei Erschöpfung drohen Node-Eviction oder System-OOM, potenziell **alle** Pods auf dem Node betroffen
- Mit Limit: Grenze ist die **Container-cgroup** → bei Erreichen killt der **OOM-Killer** einen Prozess in diesem Container (meist den Hauptprozess, höchster `oom_score`)
- Nach dem Kill: Speicher wird frei, Container wird gemäß `restartPolicy` neu gestartet
- Erkennbar an: `exitCode: 137`, `reason: OOMKilled`, steigender `restartCount`
- Sinnvoll bei bekannten **Memory Leaks**, um Schaden auf den einen Container zu begrenzen

### CPU Limits
- CPU ist **komprimierbar** – kann gedrosselt werden, ohne Prozesse zu beenden
- Ohne Limit: Container darf so viel CPU nutzen, wie der Node gerade frei hat → Performance schwankt je nach Node-Auslastung
- Mit Limit: Bei Erreichen wird der Container **gedrosselt (Throttling)**, läuft aber weiter
- **Kein Neustart, kein Kill** – nur langsamer
- Sinnvoll für **konsistentes Verhalten** über verschiedene Nodes/Cluster hinweg (z. B. Dev vs. Prod)
- Setzen: `oc set resources deployment/<name> --limits cpu=200m`

### Vergleichstabelle

| | Memory Limit | CPU Limit |
|---|---|---|
| Ressourcentyp | nicht komprimierbar | komprimierbar |
| Bei Überschreitung | Prozess wird per OOM-Killer beendet | Drosselung (Throttling) |
| Container-Neustart? | ja, gemäß `restartPolicy` | nein |
| Anwendung bleibt erreichbar? | nein (kurzzeitig, bis Neustart) | ja, nur langsamer |
| Sichtbares Signal | `OOMKilled`, `exitCode: 137`, `restartCount` ↑ | keine Fehlermeldung, nur reduzierte Performance |
| Ohne Limit betrifft Erschöpfung | ganzen Node (Eviction anderer Pods möglich) | nur die eigene CPU-Zuteilung sinkt bei Konkurrenz |
| Haupt-Einsatzzweck | Schutz vor Memory Leaks | konsistentes Verhalten über Nodes/Cluster |


## Autoscaling

- HPA skaliert automatisch die Pod-Anzahl eines ReplicationControllers, Deployments, ReplicaSets oder StatefulSets, basierend auf beobachteten Metriken wie CPU-Auslastung
- HPA läuft als Control Loop im Controller Manager und nutzt Performance Metriken vom RHOCP-Monitoring-Stack
- averageUtilization: 80 bei CPU bedeutet konkret: Verbraucht ein Pod durchschnittlich mehr als 80 % seines CPU-Requests (nicht des Limits!), wird hochskaliert.
- Achtung: wenn Limit zu niedrig gesetzt wird, kann es sein dass ein Pod die für den HPA "sichtbare" Last überhaupt erreicht, da er vorher gedrosselt wird
- HPA + VPA gleichzeitig: kritisch (gegenseitige Beeinflussung) -> lieber Kombi aus VPA Mem und HPA CPU


### Ablauf der Autoscaling-Prüfung (alle 15 Sekunden)

| Schritt | Aktion |
|---------|--------|
| 1 | Ziel-Metrik aus der HPA-Definition abrufen |
| 2 | aktuellen Metrikwert je Pod vom Metrics Server sammeln |
| 3 | Auslastung in % je Pod berechnen (Metrik vs. Resource Request) |
| 4 | Durchschnitt über alle Ziel-Pods bilden |
| 5 | Verhältnis Ziel- zu Ist-Wert berechnen |
| 6 | Replicas erhöhen oder verringern |

### Vorraussetzungen

- Resource Requests müssen definiert sein (oc create deployment erstellt diese nicht!)

Autoscaler für Deployment erstellen:
```bash
# Pod Anzahl bleibt zwischen 1 und 10
# durchschnittliche CPU-Auslastung bleibt bei 80% des angeforderten Werts
oc autoscale deployment/hello \
  --min 1 --max 10 --cpu 80%

oc get hpa

oc describe hpa hello
```

Beispiel eines komplexeren HPA für ein Deployment (nach CPU):
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello
  namespace: test1
spec:
  scaleTargetRef:     # verweist auf die Ressource, die der HPA verwaltet
    apiVersion: apps/v1
    kind: Deployment
    name: hello
  minReplicas: 1      # min und max Anzahl Pods
  maxReplicas: 10
  metrics:            # definiert die Metrik(en) für die Skalierungsentscheidung
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 80  # Ziel Durchschnittsauslastung pro Pod in %
        # Liegt die globale durchschnittliche Nutzung darüber, 
        # startet der HPA neue Pods; liegt sie darunter, löscht er Pods
```

Beispiel: Skalierung nach Memory (Memory der Anwendung muss mit Last korrelieren)
```yaml
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hello
spec:
  minReplicas: 1
  maxReplicas: 10
  metrics:
    - resource:
        name: memory
        target:
          averageUtilization: 80
```

### Vertical Pod Autoscaler (VPA)
- Ergänzung des HPA
- Skaliert indem er CPU- und Memory-Requests/-Lmitis einzelner Pods anpasst, statt Replicas hinzuzufügen oder zu entfernen
- VPA hat den Update-Modus **InPlaceOrRecreate**: wenn Node genügend Kapa hat dann passt VPA die Ressourcen ohne Neustart an
- reichen die Ressourcen nicht aus, dann wird Pod auf Node mit genügend Ressourcen neu erstellt

## Identity and Tags of Container Images

### Bestandteile eines Image-Namens

| Bestandteil | Beispiel | Bedeutung |
|-------------|----------|-----------|
| Registry-Server | `registry.redhat.io` | wo das Image liegt |
| Namespace | `rhel9` | Gruppierung/Projekt innerhalb der Registry |
| Name | `nginx-124` | Name des Images, hier inkl. Versionshinweis (Nginx 1.24) |
| Tag | `9.8` | verweist auf eine bestimmte Version des Images |

- fehlt der Tag, wird **latest** genutzt
- mehrere Tags können auf diesselbe Image Version zeigen
- **Floating-Tags** zeigen mit der Zeit auf unterschiedliche Images

### Probleme mit Floating-Tags

- wenn Container mit :latest deployed, Entwickler ein neues :latest taggt und z.B. Node ausfällt dann wird ohne mein Wissen eine neues Version des Images deployed
- ähnlich beim Hochskalieren: Neue pods ziehen neue latest-Version -> Im Deployment laufen unterschiedliche Image Versionen

### 💡 **Lösung:** Statische Image-Versionen festlegen

| Methode | Beschreibung |
|---------|--------------|
| Nicht-Floating-Tag | ein Tag verwenden, der sich konventionsgemäß nicht ändert (nur Konvention, keine technisches Verhinder|
| OpenShift Image Streams | engere Kontrolle über Image-Versionen (eigenes Kapitel) |
| SHA Image ID | statt eines Tags die eindeutige SHA-ID referenzieren |

```bash
# SHA ID ermitteln:
oc image info registry.redhat.io/rhel9/nginx-124:9.8

# bei Multi-Architecture Images:
oc image info --filter-by-os linux/amd64 \
  registry.redhat.io/rhel9/nginx-124:9.8
```

### Pull Policies

| Policy | Verhalten | Standard bei |
|--------|-----------|--------------|
| `IfNotPresent` | Ist das Image lokal auf dem Node schon vorhanden, wird es verwendet, ohne erneut zu prüfen, ob der (floating) Tag inzwischen auf eine neuere Version zeigt. Nur bei Fehlen wird gezogen. | Tag oder SHA-ID explizit angegeben |
| `Always` | OpenShift prüft immer bei der Registry, ob eine neue Version vorliegt (fragt die aktuelle SHA-ID ab). Stimmt die lokale SHA-ID überein, wird das lokale Image genutzt, sonst neu gezogen. | `latest`-Tag oder kein Tag angegeben |
| `Never` | Es wird nie gezogen, das Image muss bereits auf dem Node vorhanden sein, sonst schlägt das Deployment fehl. | – |

### Pull Policy – sinnvoller Einsatz

| Situation | Sinnvolle Policy |
|-----------|-------------------|
| Produktionsumgebung, reproduzierbare Deployments | `IfNotPresent` mit festem Tag oder SHA-ID |
| CI/CD mit `latest` während aktiver Entwicklung | `Always` (sonst bekommt man nie die neue Version) |
| Air-Gapped/Edge-Umgebung ohne Registry-Zugriff | `Never`, Images vorab auf Node bringen |

### Images von Cluster-Nodes bereinigen (Pruning)

- wenn OpenShift Pod löscht, wird Image nicht automatisch entfernt
- da Images Festplattenplatz benötigen, müssen alte Images bereinigt werden
- kubelet Prozess enthält Garbage Collector, der alle 5 min läuft
- wenn Auslastung des Image-Dateisystems über 85 %, dann werden die ältesten ungenutzten Images entfernt
- Bereinigung stoppt, wenn Auslastung < 80%
- Schwellenwerte des Garbage Collectors lassen sich über die KubeletConfig-Custom-Resource anpassen

## Update Application Image and Settings

- Moderne Anwendungen trennen Code, Konfiguration und Daten lose voneinander
- Konfiguration und Daten sind nicht fest in die Software einprogrammiert, sondern werden aus einer externen Quelle geladen
- Das ermöglicht es, dieselbe Anwendung in unterschiedlichen Umgebungen zu betreiben, ohne den Quellcode zu ändern
- **Konfiguration/Daten**: ConfigMap, Secret, Volume
- **Code**: Container-Image

### Deployment-Strategien im Überblick

| Strategie | Prinzip | Ausfallzeit | Voraussetzung |
|-----------|---------|-------------|----------------|
| `RollingUpdate` (Standard) | Instanzen werden nacheinander ersetzt, alte und neue Version laufen zeitweise parallel | keine | Versionen müssen kompatibel nebeneinander laufen können |
| `Recreate` | Alle alten Instanzen werden zuerst gestoppt, danach neue gestartet | ja, während der Umschaltung | keine Parallelität nötig |

RollingUpdate-Strategie Ablauf (Beispiel):

1. Einige Instanzen laufen noch mit der alten Version (v1). OpenShift startet eine neue Instanz mit v2. Da diese noch nicht bereit ist, bedienen nur v1-Instanzen Anfragen.
2. Die v2-Instanz ist bereit und übernimmt Anfragen. OpenShift fährt eine v1-Instanz herunter und startet eine weitere v2-Instanz. Beide Versionen bedienen gleichzeitig Anfragen.
3. Die nächste v2-Instanz ist bereit. OpenShift fährt die verbleibende v1-Instanz herunter.
4. Keine alten Instanzen mehr übrig – Update erfolgreich, ohne Ausfallzeit.

### Parameter der RollingUpdate-Strategie

| Parameter | Bedeutung |
|-----------|-----------|
| `maxSurge` | wie viele Pods OpenShift zusätzlich über die normale Replica-Zahl hinaus erstellen darf |
| `maxUnavailable` | wie viele Pods OpenShift unter die normale Replica-Zahl absenken darf |

💡 **wichtig:** Readyness Probe ist notwendig, sonst wird Traffik an noch nicht bereitse Pods geschickt!

Recreate-Strategie Ablauf (Beispiel):

1. Instanzen laufen mit v1.
2. OpenShift skaliert auf 0 Instanzen herunter → Ausfallzeit beginnt, keine Instanz bedient Anfragen.
3. OpenShift skaliert neue v2-Instanzen hoch, während diese starten, hält die Ausfallzeit an.
4. Sobald die neuen Instanzen laufen, endet die Ausfallzeit.

Nicht empfohlen für hochverfügbare Anwendungen (z. B. medizinische Systeme). Sinnvoll, wenn:

- unterschiedliche Code-Versionen nicht gleichzeitig laufen dürfen
- vor dem Start der neuen Version Daten migriert/transformiert werden müssen

### Anwendungen ausrollen (oc Rollout)
- Aktualisiert man das Deployment-Objekt, rollt OpenShift die Änderung automatisch aus. 
- Werden mehrere Änderungen nacheinander angewendet (Image, Env-Variable, Readiness Probe), löst jede einzelne einen eigenen Rollout aus.
- Um mehrere Rollouts zu vermeiden: Rollout pausieren, alle Änderungen bündeln, dann fortsetzen:

```bash
# Rollout pausieren
oc rollout pause deployment/myapp

# Mehrere Änderungen bündeln
oc set image deployment/myapp \
  nginx-120=registry.access.redhat.com/ubi9/nginx-120:1-86
oc set env deployment/myapp NGINX_LOG_TO_VOLUME=1
oc set probe deployment/myapp --readiness --get-url http://:8080

# Rollout fortsetzen – wendet alle Änderungen gebündelt an
oc rollout resume deployment/myapp

# Alternative -> die replicas auf 0 setzen, änderungen implementieren, hochskalieren
oc create deployment myapp2 \
  --image registry.access.redhat.com/ubi9/nginx-120:1-86 --replicas 0

# aktueller Status
oc rollout status deployment/<name>` 

# auf vorherige Version (beliebige Version)
oc rollout undo deployment/myapp2 (--to-revision N)

# Verfügbare Revisionen auflisten
oc rollout history deployment/myapp2

# Details zu bestimmten Revision:
oc rollout history deployment/myapp2 --revision 1

# Benutzerdefinierte Beschreibung hinzufügen
oc annotate deployment/myapp2 \
  kubernetes.io/change-cause="Image updated to 1-86"

```

### ReplicaSets
- beim Rollout eines Deployments erstellt OpenShift ein ReplicaSet, das zuständig für das Erstellen und Überwachen eines Pods ist
- wenn Pod ausfällt, dann erstellt ReplicaSet einen neuen
- bei Deployment Aktualisierung wird RS nicht verändert, sondern neues RS erstellt und rollt gemäß Strategie aus
- während Rolling Updates koordinieren sich alte und neue RS, nach Abschluss bleibt altes RS mit 0 Pods erhalten
- dies zum Zweck eines Rollbacks
- Attribut **.spec.revisionHistoryLimit** im Deployment legt fest, wie viele alte ReplicaSets aufbewahrt werden
